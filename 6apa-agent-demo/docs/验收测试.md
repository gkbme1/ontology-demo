### 2. Agent Loop：22 项断言全通过

```bash
ONTOLOGY_BASE_URL=http://localhost:8700 python3 -m tests.test_agent_loop
```

用脚本化假 LLM 替换模型，验证 Runtime 本身（本体调用全部是真的）：

| 用例 | 验证点 |
| --- | --- |
| 多步 Tool 链路 | 检索设备 → 查详情 → 查关系 → 作答；3 次工具调用、4 轮模型调用、3 条 tool 结果确实回灌进下一轮 messages |
| 实体上下文 | 当前设备写入会话（equip-8170434d）；第二轮提问时作为 system 消息注入 |
| 工具预算 | 模型无限要工具时，第 N 次后不再执行，且强制收口作答 |
| 异常处理 | 不存在的工具 / 缺必填参数 / 把名称当 ID 传（404）——三种都被捕获、回灌、不崩溃，最后仍能作答 |
| 大返回体 | 不给 limit 时自动补默认分页；334 KB 详情压到 5,974 字符，`total` 保留，附裁剪说明 |
| 历史裁剪 | 6 轮对话后按整轮丢弃最早 4 轮，没有出现孤立的 `tool` 消息 |

## 二、需要填 Key 后现场跑（需求文档第十六章）

> 工艺调查案例建议按 `docs/工艺调查案例.md` 里「合格的回答长什么样」逐条对照验收，
> 重点看三件事：有没有先用限值确认异常成不成立、没有测点的影响因素有没有如实说、
> 模拟数据有没有声明。

```bash
# .env 填好 LLM_API_KEY 后
python3 -m scripts.cli
```

| # | 提问 | 期望行为 | 关注点 |
| --- | --- | --- | --- |
| 1 | 6-APA 生产车间有多少设备？ | 调 `query_ontology_overview` | 应直接取 overview，而不是翻设备列表去数 |
| 2 | 介绍一下 Dev_10_一层排渣泵 | `query_equipment_list(keyword)` → `query_equipment_detail(equip-…)` | 能否自己完成"名称 → ID"这一步 |
| 3 | 多轮上下文：①介绍一下一层排渣泵 ②它有哪些参数？ ③它有哪些DCS点？ ④它和哪些设备有关联？ ⑤它的上游是什么？ | 全程不重复设备名 | "它"是否每轮都指向同一台设备 |
| 4 | 水解工段有哪些设备？这些设备之间有哪些重要关系？ | 组合 `process-areas` + `equipment` + `relations` | 是否自主组合多个工具 |
| 5 | 从本体中，你能告诉我目前有哪些类型的知识吗？ | 从 `categories` 出发，按需展开 classes / properties / relations / rules 等 | 规则等空数据源是否被如实报告为"暂无"，而不是编造 |
| 6 | 分析一下水解工段的设备关系结构，哪些设备关联较多，这些关系主要属于什么类型？ | `summarize_area_relations`（"水解工段"有歧义时先确认是 S11 酶法水解） | 计数是否与本体全量一致（不漏类别）；是否区分"本体真实数据"与"基于数据的分析" |
| 7 | 昨天水解罐温度异常，帮我调查一下原因 | `investigate_process_anomaly` 一次完成：限值 → 历史值确认异常 → 因果关系找原因 → 测点可用性 → 同期历史比对 → 分层结论 | 三个影响因素都没有测点，是否**如实说明无法用数据验证**；是否引用 PL001 而不是自设阈值；是否声明模拟数据 |
| 8 | 反应体系 pH 昨天波动比较大，是不是氨水加料引起的？ | `verify_process_influence`：本体路径与方向 + 两端曲线比时间/方向/幅度 | 结论有没有显式标注是分析；对不上时会不会硬凑 |
| 9 | 水解进料换热温度偏高，可能是什么引起的？用数据验证一下 | `investigate_process_anomaly`；关系是**负向影响**：冷盐水流量下降 → 换热温度上升才算对得上（程序按正负号传播预期方向） | 是否看了关系方向，而不是默认同涨同落 |

### 每个测试都该顺手检查的

- [ ] 右侧执行过程面板显示的工具调用序列，与回答内容对得上
- [ ] 回答里出现的设备名/位号/数字，能在工具返回结果里找到出处
- [ ] 出现 `truncationNote` 时，回答有没有把样本当全部
- [ ] 没有任何思维链 / 模型内部推理被显示出来
- [ ] `logs/turns.jsonl` 里这一轮的轨迹完整，且不含 API Key

### 如果模型表现不理想

优先改 `backend/prompts/system_prompt.txt` 和 `backend/tools/ontology_tools.py` 里的工具描述——
这两处是调模型行为的正确位置。改完 Prompt 调 `POST /api/prompt/reload` 即可生效，不用重启。

**不要**为了让某个测试通过而在代码里加针对该问题的分支，那会直接破坏这个 Demo 想证明的东西。
