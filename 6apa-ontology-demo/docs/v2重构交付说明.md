# 本体 v2 重构交付说明

依据 2026-09-27 提供的 8 个数据文件重构。**对外接口字段名一个没删**，变的是条目内容、
新增字段与 areaId 的取值形式。下面按"你会直接感觉到的变化 → 接口清单 → 代码改动 → 需要你确认的事"来写。

---

## 一、最重要的一件事：工段口径换了

旧版的「生产工段」实际是按 **DCS 控制站** 划分的，一个控制站里混着多个工艺工段。
交叉统计能直接看出来：

```
站13 → S10 水解辅料配制 164 点、S11 酶法水解 470 点、S12 萃取与反萃 244 点、S15 结晶辅料 45 点、S99 备用 60 点
站30 → S16 干燥 90 点、S07 抽提 47 点、S06 脱色 26 点、S12 萃取 25 点、S13 结晶 11 点、…
```

所以旧版回答"酶法水解工段有哪些设备"时，会把萃取、结晶辅料的设备一起带出来。
v2 改用流程图口径，24 个工段（S01–S23 + S99 备用），点表、关系表、限值表、规则表、
对象映射全部对齐到它。**控制站从"分类依据"降级为"属性"**（`station` 字段含义不变）。

### 由此带来的模型变化：设备可以跨工段

1340 台设备中有 **46 台**的点位落在多个工段（例如 `:Dev_10_离心机A` 同时在 S01 和 S02）。
处理方式：

| 字段 | 含义 |
| --- | --- |
| `areaId` / `areaCode` / `areaName` | **主工段**，取自「设备统计」表的声明 |
| `areaIds` / `areaCodes` / `areaNames` | 该设备点位实际覆盖的全部工段 |
| `areaSpan` | 覆盖的工段数；大于 1 时 Agent 会在回答里说明 |

`?areaId=` 过滤按**任一命中**处理，比只匹配主工段符合直觉。
设备跨控制站的是 0 台（已核查），所以 `station` 仍是一对一。

### areaId 的三种写法

按你的选择，工段 ID 直接用编号：`area-S01`。凡是接受 `areaId` 的地方，
**`area-S11` / `S11` / `酶法水解` 三种写法等价**，Agent 可以直接传工段名。

## 三、v2 带来的三个新能力

**1. 工艺量到位号不再靠猜。** 关系表里 1118 条关系自带「关联DCS位号」，另有 622 条
「绑定测点」关系（客体类型 DCS测点）。拆出的 1943 个位号里 1917 个能在点表中精确命中。
对象匹配因此多了一条**最高优先级**策略 `RELATION_TAG_BINDING`（关系表位号绑定），
人工映射表降为兜底。效果很直接——v1 里「釜内反应温度」的三个影响因素一个测点都没有，
v2 里四个影响因素全部可测：

| 影响因素 | 关系 | 测点数 |
| --- | --- | --- |
| RB进料温度 | 正向影响 | 5 |
| 硼酸溶液温度 | 正向影响 | 5 |
| 夹套热水/蒸汽加热量 | 正向影响 | 5 |
| 热水阀HV_1301 | 影响 | 12 |

三条后果（固定化酶活力稳定性、6-APA热降解损失率、酶催化水解反应速率）仍然没有测点，
这是真实的数据缺口，Agent 必须如实说明。

**2. 规则从 0 条变 71 条，且与限值联动。** 37 条规则的阈值写的是「见 PLxxx」，
接口用 `limitRefs` 解析出引用的限值编号；`draft: true` 标出「【草案·待现场确认】」的条目。

**3. 工段衔接可查。**「上游停了会影响谁」第一次有据可查——40 条衔接，每条带衔接物料与位号。

### 新增 4 个接口

```
GET /api/ontology/equipment-groups              标准设备组（120 个）
GET /api/ontology/equipment-groups/{id}         设备组详情（id 可传 egrp-xxx / :GroupUri / 设备组名称）
GET /api/ontology/area-flow                     全流程工段衔接（40 条）
GET /api/ontology/process-areas/{id}/flow       单个工段的上下游
```

### 关于 `?view=compact`

v2 一条关系的完整返回体约 1.8 KB（多了 URI、来源、位号、依据等），
查某个对象的 20 条关系就是 35 KB，调用方的返回体预算很容易被撑爆——
Agent 实测只能看到 7 条，恰好把因果关系切没了。
`view=compact` 去掉追溯字段，一条约 300 字节，20 条完整放得下。
遍历因果链时用 compact，需要来源行号与 URI 时再用默认视图。

## 五、顺带修的两个问题

**启动慢。** pandas 每调一次 `read_excel(path, sheet_name=...)` 都会把整个工作簿重新解析一遍，
v2 的点表要读 7 张 Sheet，关系表 5 张，共享字符串表被反复解析——索引构建要 **36 秒**。
改成按 (路径, 修改时间) 缓存 `pd.ExcelFile`，整本只解析一次，加上给设备/参数名建索引
（对象匹配原本是 1174 × 11697 次全表扫描），降到 **9.5 秒**。

**首个请求顶着构建时间。** 索引原本是懒加载，第一个请求要等十几秒，很容易被误判成"服务没起来"。
现在进程启动时预热，日志会打印一行：

```
INFO: 本体索引已就绪：24 工段 / 1340 设备 / 10680 点位 / 2252 关系，耗时 9.8s
```

FastAPI 走 `startup` 事件，Starlette 回退路径走 `lifespan`（Starlette 1.0 起没有 `on_startup`）。

## 六、发现的数据问题（都进了 data-quality，没有自行修改原始数据）

| 问题 | 数量 | 处理 |
| --- | --- | --- |
| **S99 编号含义冲突**：点表「工段划分」里 S99 = 备用/未定义点；限值与规则的「工段取值(参考)」里 S99 = 跨工段协同 | 1 处定义冲突，影响 3 条限值 | 按各自文件口径分别解析，**不合并**；报 warning |
| 关系表「关联DCS位号」单元格被写截断（值以省略号结尾） | 26 个位号 | 逐条列出关系 ID 与行号，无法解析 |
| 点位明细的「标准设备组(本体)」有 183 种取值，设备主数据只登记 120 个组 | 65 个组名对不上 | 以设备主数据为权威组注册表；点表里的值保留为文字标签，不强行合并 |
| 设备主数据有 2 个组在点表中找不到点位 | 2 | 报 info |
| 流程画面与点表不一致项 | 11 | 原样透出为待现场确认清单 |
| 画面可见但点表未收录的位号 | 42 | 原样透出为建议补录清单 |
| 设备跨工段 | 46 | 报 info，说明这是 v2 口径下的正常现象 |

data-quality 现在 26 项检查、**0 个 error**（warning 746 / info 1506）。
问题数比 v1 多，是因为数据量涨了一个量级（关系 71→2252、关系对象 71→1174），不是质量变差。

## 七、Agent 侧同步改动

- 工具从 30 个增到 **33 个**：新增 `query_equipment_groups`、`query_equipment_group_detail`、`query_area_flow`。
- `query_relation_entities` 加了 `keyword` / `areaId` / `limit` / `offset`（1174 个对象不分页必被裁剪）。
- `query_relations` 加了 `view` 参数，工具说明里写明遍历因果链要用 compact。
- 系统提示新增「工段口径」一节：工段不是控制站、一台设备可能跨工段、areaId 三种写法等价。
- ID 约定补上 `area-S01`、`egrp-`、`PL001`、`R-G-01`。
- 内置案例里的工段名改成 v2 口径；INV-05 / INV-06 两条案例的对象在 v2 中不存在了
  （氨水加料流量、换热器冷盐水流量、夹套伴热蒸汽流量），换成 v2 里真实存在且两端可测的路径：
  稀硫酸注入流量 → 一阶段酸化pH、浓硫酸加入流量 → 稀硫酸浓度。
